## 🎯 What This Project Is

**ML Based Cyber Attack Detection in Simulated Networks** is a full-lifecycle Intrusion Detection System (IDS) that demonstrates — concretely, with evidence at every step — how a machine learning model can distinguish normal network behaviour from live cyber attacks in real time.

The project deliberately avoids the shortcut taken by most academic IDS work. Instead of downloading a ready-made dataset like NSL-KDD or CICIDS2017, **every packet was produced inside a controlled virtual network built specifically for this project.** Attacks were launched from a real Kali Linux machine against a real victim server; benign traffic was generated by genuine service interactions. The result is a dataset the authors understand completely, down to the individual capture session that produced every row.

The system spans two operational phases:

1. **Offline Training Phase** — packet captures are converted into a labelled feature matrix, and five ML classifiers are trained and benchmarked to select the strongest.
2. **Live Deployment Phase** — the winning model is loaded onto a dedicated monitoring sensor that sniffs traffic, classifies it flow-by-flow every second, and streams verdicts to a real-time web dashboard.

---

## 💡 Why It Matters

Signature-based intrusion detection (the traditional approach) can only catch attacks it already has a rule for. This project explores the alternative: a **behavioural, statistics-driven model** that learns the *shape* of an attack — its packet rates, flag distributions, and port-spread patterns — rather than matching fixed signatures.

The payoff is measurable. The final Random Forest classifier reaches **99.74% accuracy** across five classes, and the deployed system raises an alert within roughly **one second** of an attack beginning. Just as importantly, the project shows the *entire* chain of reasoning — why each feature was chosen, why a hub was used instead of a switch, why heuristic guards back up the model — making it a genuine teaching artifact, not just a score on a slide.

## 🔥 The Five Traffic Classes

The system classifies every one-second flow window into exactly one of five categories:

| Label | Class | Threat Level | Attack Tool | Signature Behaviour |
|:-----:|:------|:------------:|:------------|:--------------------|
| `0` | **Normal** | 🟢 Low | — | Legitimate ping, HTTP, SSH and FTP sessions |
| `1` | **Ping DoS** | 🟠 High | `ping -f` | High-rate ICMP echo flood, near-zero inter-packet gap |
| `2` | **SYN Flood** | 🔴 Critical | `hping3 -S --flood` | Thousands of half-open TCP handshakes, 100% unanswered |
| `3` | **Nmap Scan** | 🟡 Medium | `nmap -sS -p-` | Sequential port sweep, very high unique-destination-port entropy |
| `4` | **Brute Force** | 🟠 High | `hydra ... ssh` | Repeated SSH auth attempts, elevated RST ratio on port 22 |

## ✨ Key Features

- 🧪 **100% self-generated dataset** — 8 hand-captured PCAP files across 8 dedicated capture sessions, zero third-party data
- 🔬 **34 engineered flow features** — volume, rate, protocol mix, all six TCP flags, port diversity, plus 3 custom composite discriminators
- 🤖 **5 classifiers benchmarked head-to-head** — Random Forest, Decision Tree, KNN, Logistic Regression, SVM, each with full classification reports and confusion matrices
- ⚡ **Sub-second real-time detection** — 1-second sliding capture window with per-flow classification
- 🧠 **Hybrid ML + heuristic decision logic** — model predictions reinforced by deterministic guards to suppress false positives and catch obvious floods
- 🎯 **True attacker attribution** — multi-stage flow-direction resolution correctly identifies the initiator, not the victim
- 📊 **Live web dashboard** — dark-themed operations console refreshing every 500 ms with charts, a rolling detection table, topology view, alerts and toast notifications
- 📁 **Date-structured forensic logging** — every classification appended to per-session CSV audit logs organised into daily folders
- 🌐 **Fully reproducible** — the GNS3 project file, all PCAPs, the dataset, and all model artifacts are included so the entire experiment can be rebuilt or re-run

## 🌐 Lab Topology

The whole environment was built and run **inside GNS3**, hosted on the **GNS3 VM** with **VMware Workstation** providing the virtual machines. Four VMs are wired through a single **Ethernet hub** in a star topology, giving the IDS monitor node complete visibility of every frame exchanged between the attacker, the victim, and the legitimate client — no managed-switch port mirroring required.

<div align="center">
<img src="docs/screenshots/01-topology.jpg" alt="GNS3 lab topology diagram" width="88%">
</div>

| Node | Role | IP Address | Operating System | Purpose |
|:-----|:-----|:-----------|:-----------------|:--------|
| **Kali Linux** | Attacker | `192.168.188.131` | Kali Rolling | Launches all four attack types |
| **Lubuntu Server** | Victim | `192.168.188.130` | Lubuntu | Runs Apache2, OpenSSH, vsftpd |
| **Lubuntu Client** | Legitimate user | `192.168.188.133` | Lubuntu | Generates benign background traffic |
| **Ubuntu Monitor** | IDS sensor | `192.168.188.132` | Ubuntu | Runs the Scapy sniffer + Flask dashboard |
| **Ethernet Hub** | Network fabric | — | — | Floods frames to all ports for full visibility |

> 💡 **Why a hub, not a switch?** A switch forwards frames only to their intended destination port, which would blind the monitor to traffic between other hosts. A hub broadcasts every frame to every port, so the IDS sensor sees *all* traffic without requiring managed-switch port mirroring (SPAN). This is the single most important topology decision in the whole lab — without it, passive monitoring is impossible.

> 🧠 **The hardest problem in the dataset was making benign SSH look benign.** A naive model will flag *all* port-22 traffic as an attack. To prevent this, the benign SSH capture was scripted (`tools/ssh_traffic.sh`) to cover **seven distinct behavioural patterns**: initial handshakes, small interactive keystrokes, idle sessions with keepalives, large command output, SCP file transfers (both directions), mixed command-then-pause activity, and many rapid short sessions. This taught the model what legitimate SSH *actually* looks like, so it learned to key on brute-force-specific signals (RST bursts, ephemeral source-port cycling) rather than the port number alone.

## 🔬 Phase 3 — Feature Engineering

`pcap_to_csv.py` is the heart of the training pipeline. It reads each PCAP, slices the packet stream into **1-second windows**, and computes **34 statistical and protocol-level features** for each window. Every window inherits the label of its source file, so the labelling is automatic and consistent.

### Class Distribution

| Label | Class | Windows | Share |
|:-----:|:------|--------:|------:|
| `0` | Normal | 1,299 | 85.4% |
| `4` | Brute Force | 171 | 11.2% |
| `1` | Ping DoS | 18 | 1.2% |
| `2` | SYN Flood | 17 | 1.1% |
| `3` | Nmap Scan | 16 | 1.1% |
| | **Total** | **1,521** | **100%** |

> ⚖️ **On the imbalance:** flood attacks are, paradoxically, *underrepresented* by window count — they cram tens of thousands of packets into just a handful of 1-second windows, while benign traffic spreads thinly across many. This is handled two ways: `class_weight="balanced"` penalises the model more heavily for misclassifying rare classes, and the train/test split is **stratified** so every class appears in both partitions in proportion. The 99.74% figure is therefore not an artifact of the majority class dominating.

| Rank | Model | Accuracy | Configuration |

### Exported Artifacts

```
models/best_ids_model.pkl      # the trained Random Forest classifier
models/feature_columns.pkl     # exact ordered list of the 34 feature names
models/label_mapping.json      # {0:"Normal", 1:"Ping DoS", 2:"SYN Flood", 3:"Nmap Scan", 4:"Brute Force"}
```

> 🔑 **Why `feature_columns.pkl` is critical:** scikit-learn models are sensitive to column *order*, not just column names. At inference time the live sniffer rebuilds a fresh feature DataFrame and reorders it with `row = row[feature_columns]` before calling `.predict()`. This guarantees the exact same column ordering used in training, eliminating an entire class of silent, hard-to-debug prediction errors.

## ⚡ Phase 5 — Real-Time Detection Engine

The deployed sensor (`Ubuntu Deployment Phase/app.py`) runs **two concurrent threads** sharing state behind a mutex:

1. A **Scapy sniffer loop** that captures, groups, extracts features, classifies, and logs.
2. A **Flask web server** that serves the dashboard and a `/status` JSON endpoint.

### Capture Filtering (BPF)

A precisely scoped Berkeley Packet Filter restricts capture to the three lab hosts and **explicitly excludes** the monitor's own address, the gateway, multicast, and broadcast — so the IDS never analyses its own dashboard traffic (which would create a runaway feedback loop) and never wastes cycles on irrelevant chatter.

<div align="center">
<img src="docs/screenshots/23-bpf-capture-filter.jpg" alt="BPF capture filter configuration" width="88%">
</div>

```python
INTERFACE = "ens33"
BPF_FILTER = (
    "ip and "
    "(host 192.168.188.130 or host 192.168.188.131 or host 192.168.188.133) "
    "and not host 192.168.188.132 "   # exclude the monitor itself
    "and not host 192.168.188.128 "
    "and not host 192.168.188.1 "     # exclude the gateway
    "and not net 224.0.0.0/4 "        # exclude multicast
    "and not host 255.255.255.255"    # exclude broadcast
)
```

<details>
<summary><b>🧪 Custom Composite Features (3) — the secret sauce</b></summary>

These three were engineered specifically to solve the **hardest classification problem in the dataset: separating legitimate SSH from SSH brute force.** Both are TCP traffic on port 22, so simple features can't tell them apart. These composites can:

| Feature | Formula | Rationale |
|:--------|:--------|:----------|
| `port_entropy` | `unique_dst_ports ÷ (packet_count + 1)` | High when few packets touch many ports → hallmark of a port scan |
| `port22_rst_product` | `port_22_count × rst_count` | Non-zero only when SSH traffic *and* connection resets co-occur → the exact fingerprint of failed authentication attempts |
| `port22_src_diversity` | `port_22_count × unique_src_ports` | Brute-force tools cycle through many ephemeral source ports; a genuine human SSH session uses very few |

</details>

## 🏗️ Design Decisions & Engineering Notes

Three pieces of the deployment logic deserve special attention — they're what separate this from a naive `model.predict()` demo:

### 1. True attacker attribution (`determine_flow_direction`)

Rather than blindly trusting the first packet's source, the system determines the *real* initiator of a flow through a prioritised cascade:

1. Look for a lone `SYN` with no `ACK` — the classic connection initiator.
2. Failing that, look for an ICMP echo *request* (`type 8`).
3. Failing that, look for traffic toward a well-known service port (20/21/22/80/443).
4. Only as a last resort, fall back to the most frequent IP pair.

The result: the dashboard correctly reports the **Kali attacker** as the source, not the victim replying to it.

### 2. Heuristic guards reinforcing the ML model

Pure ML on 1-second windows can wobble on tiny samples, so two deterministic rules back it up:

- An `Nmap Scan` prediction on a window of **fewer than 5 packets** is downgraded to `Normal` — suppressing false positives on sparse, ambiguous traffic.
- Any window with **≥15 ICMP packets and zero TCP/UDP** is force-classified as `Ping DoS` — catching an obvious flood even if the model hesitates.

### 3. Alert hold + recent-attack memory

Real attacks are bursty, not continuous. A 5-second `ALERT_HOLD_TIME` keeps the dashboard in its alert state between bursts, and a `recent_attacks` map remembers attacker↔victim pairs so a brief mid-attack lull isn't misread as "safe". This makes the live display stable and trustworthy instead of flickering.

## ⚠️ Limitations & Future Work

An honest accounting of where the system stands and where it could go:

- **Closed-world assumption** — the model classifies into 5 known classes only. A novel attack will be forced into the nearest class rather than flagged as unknown. *Next step: add an anomaly/one-class detector as a second stage.*
- **Small, imbalanced dataset** — three attack classes have fewer than 20 windows each. The 99.74% reflects a controlled lab, **not** production traffic. *Next step: longer and more varied captures, plus synthetic augmentation for rare classes.*
- **Lab-specific configuration** — `INTERFACE` and `BPF_FILTER` are hardcoded to this topology. *Next step: move them to a config file or CLI flags.*
- **Encrypted-payload blindness** — detection is purely flow-statistical; there is no deep packet inspection (which is also what makes it privacy-preserving).
- **Detection, not prevention** — the system alerts but does not block. *Next step: an optional `iptables`/`nftables` auto-mitigation hook.*
- **Single sensor point** — one hub-attached monitor. *Next step: distributed sensors feeding a central aggregator.*
